# 前端协作约定

## 1. 文档目标

本文档用于沉淀“用户与 Codex 在前端页面设计和实现过程中的协作约定”，减少反复沟通成本，帮助后续迭代更稳定地对齐预期。

本文档重点不是记录页面功能，而是记录已经验证有效的协作方式、表达方式与执行方式。

---

## 2. 当前适用范围

当前约定主要适用于以下任务：

- 首页、Dashboard、详情页等前端页面改版
- 参考站点或参考截图驱动的页面重构
- 样式收口、布局调整、产品化视觉统一

---

## 3. 已确认的协作方式

### 3.1 大改前先给出实现方案

开始做页面级改版前，先给出本轮实现方案，至少包含：

- 本轮目标
- 改动范围
- 涉及文件
- 完成标准

在用户确认前，不直接开始大范围代码修改。

---

### 3.2 有参考图或参考站时，先抽取硬约束

当用户给出参考网站或参考截图时，不能直接凭感觉“参考一下”就开始改。  
应先抽取并复述本轮硬约束，例如：

- 是否全宽布局
- 是否允许局部背景色
- 是否需要单列或三栏
- 是否要减少文字
- 哪些元素必须删除
- 哪些元素必须保持

后续实现和验收都应对照这份硬约束进行。

---

### 3.3 用户要求“仿照 / 复刻”时，先对齐布局关系，再做自主发挥

当用户明确要求“仿照参考图”时，优先还原以下内容：

- 页面骨架
- 区块关系
- 视觉主次
- 信息密度

不要过早加入自主的产品化发挥或额外模块。  
先把“像不像”做对，再补自己的优化。

---

### 3.4 大改代码按步骤小 patch 执行，不整文件重写

页面级重构默认按以下顺序进行：

1. 先改骨架
2. 再改关键区域
3. 再收样式
4. 最后做验证

尽量避免整文件覆盖式改写，优先使用多次小 patch，降低回退和工具限制风险。

---

### 3.5 已被明确否定的设计点，后续轮次不能加回

如果用户已经明确否定某类设计处理，例如：

- 局部背景染色
- 双栏 Hero
- 过多说明文字
- 重标题海报感

那么后续轮次不能擅自再次加回。  
每轮修改前应先检查这些“禁止项”。

---

### 3.6 前端评审以真实页面为准，不只看代码

页面改动后，至少做两类验证：

- 执行 `cd frontend && npm run build`
- 实际访问 `http://localhost:5173/` 对应页面检查效果

如果是登录后页面，优先在真实登录态里验证。

---

### 3.7 视觉评审前先确认浏览器缩放比例

在判断“页面过大 / 过小 / 偏上 / 偏下”前，先确认浏览器缩放比例是否为 `100%`。  
避免把本地浏览器缩放问题误判为页面布局问题。

---

### 3.8 文案默认收短，宁少勿多

页面文案默认按以下原则处理：

- 先保留必要文案
- 再评估是否需要补解释
- 不把页面写成说明文档

对于首页、登录页、注册页、详情页等高频页面，默认优先做“少文字、强结构”。

---

### 3.9 模块文档按阶段总结更新，不逐轮流水账

小样式调整和连续微调默认不逐轮写入模块文档。  
只有完成一段可独立说明的页面重构或阶段性结果后，再补一条总结性记录。

---

## 4. 推荐的单轮协作节奏

后续前端页面任务，推荐按以下节奏协作：

1. 用户给目标、参考图或参考站
2. Codex 抽取硬约束并给出本轮方案
3. 用户确认后开始实现
4. Codex 分步骤小 patch 改代码
5. 构建与页面验证
6. 汇报：
   - 修改了哪些文件
   - 实现了什么
   - 影响了什么
   - 是否做过验证
7. 用户再决定继续收细节还是切到下一页

---

## 5. 当前结论

后续前端协作默认遵循：

- 先约束，后实现
- 先骨架，后细节
- 先像参考，再做发挥
- 先真实页面验证，再讨论下一轮
