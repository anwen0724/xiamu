# Repository Guidelines

## 1. Scope
- 本文件提供仓库级高优先级协作约束
- 详细规范采用渐进式披露，通过 `docs/` 或其他专门文档继续阅读
- 若子目录存在更近一级 `AGENTS.md`，优先遵循更近一级规则

## 2. Universal Rules

### 2.1 Collaboration Workflow
- 开始实现前先给出本轮方案
- 方案至少包含：目标、范围、涉及文件、完成标准
- 在得到确认前，不直接开始大范围代码修改

### 2.2 Change Control
- 优先小步修改，避免一次性整文件重写
- 有参考资料时，先抽取硬约束，再开始实现
- 已被明确否定的方案、设计点或方向，不得擅自加回

### 2.3 Reporting
- 每次修改完成后，先汇报本次改动，再进入下一步
- 汇报至少包含：修改了哪些文件、实现了什么、影响了什么、是否做过验证

### 2.4 Verification
- 至少执行与改动范围匹配的验证
- 评审不只看代码，还要看真实运行结果
- 如项目已接入构建、测试、lint、type-check，应按改动范围执行相应校验

### 2.5 Documentation
- 文档更新遵循最小改动原则
- 先更新对应模块文档，再视情况更新总控文档

### 2.6 Safety
- 不覆盖用户已有修改
- 不执行未获确认的高风险操作
- 不提交密钥、密码、令牌或本地运行产物

### 2.7 Definition of Done
- 代码实现完成
- 验证完成
- 修改结果已汇报
- 相关文档已按需要同步

## 3. Stack Rules

### 3.1 Frontend
- 页面、组件、布局、状态、接口分层明确
- 页面级改版先确认布局骨架和硬约束
- 详细规范见：`docs/<前端规范文档路径>`

### 3.2 Backend
- 接口层保持轻量，业务逻辑进入服务层
- 数据访问、业务编排、外部集成职责分离
- 详细规范见：`docs/<后端规范文档路径>`

### 3.3 Data / API
- 数据结构、接口行为、状态流转变化时需同步文档
- 详细规范见：`docs/<接口或数据库规范文档路径>`

### 3.4 Testing
- 核心改动需补充与改动范围匹配的验证
- 详细规范见：`docs/<测试规范文档路径>`

### 3.5 Scripts / Tooling
- 脚本、自动化工具、构建工具职责清晰独立
- 涉及本地依赖或系统依赖时，应补充运行说明
- 详细规范见：`docs/<脚本或工具规范文档路径>`

## 4. Project Rules

### 4.1 Summary
- 项目简介
- 当前阶段
- 当前重点

### 4.2 Repository Map
- 代码目录
- 配置目录
- 文档目录
- 测试目录
- 脚本目录

### 4.3 Read Before Work
- 开发前必读文档
- 各类任务对应的详细文档入口

### 4.4 Boundaries
- 项目特有架构边界
- 禁止混写的层次
- 特殊流程约束

### 4.5 Commands
- 运行命令
- 测试命令
- 构建命令
- 本地环境要求

## 5. Extended References

- 后端规范：`docs/<...>`

- 文档维护规范：`docs/<...>`

## 6. Subtree Overrides
- 子系统差异明显时，可在子目录新增 `AGENTS.md`
- 更近一级规则优先
- 子规则只写差异部分
