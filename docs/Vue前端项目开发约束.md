# Vue 前端项目开发约束

## 1. 文档目标

本文档用于沉淀一套可复用的 Vue 前端项目开发约束，适合作为新项目初始化或多人协作时的默认基线。

本文档不绑定具体业务领域，也不依赖某一个仓库结构；重点是统一目录组织、职责边界、命名方式与最低开发要求。

---

## 2. 适用范围

默认适用于以下技术栈：

- Vue 3
- TypeScript
- Vite
- Vue Router
- Pinia

如项目使用 TanStack Query、VueUse、Vitest、ESLint、Prettier 等工具，也可直接沿用本文档中的分层思路。

项目初始化阶段，默认优先使用 Vue 官方脚手架创建项目，再按本文档对生成后的项目结构和分层进行整理。

推荐命令：

```bash
npm create vue@latest
```

推荐做法：

- 先使用 Vue 官方脚手架初始化项目
- 再根据实际需要补充 `api`、`pages`、`layouts`、`composables`、`stores`、`queries` 等目录
- 最后统一调整路由、状态管理、样式组织和命名方式

一句话原则：

先用官方方式建项目，再按统一规范收口结构。

---

## 3. 推荐目录结构

推荐以 `src/` 为核心，按职责分层组织：

```text
src/
  api/             # 接口请求与接口类型映射
  assets/          # 静态资源
  components/      # 可复用组件
  composables/     # 组合式逻辑复用
  layouts/         # 页面布局骨架
  pages/           # 路由页面
  plugins/         # 插件注册与初始化
  queries/         # 服务端状态查询（可选，使用 Query 类库时启用）
  router/          # 路由配置
  stores/          # 客户端全局状态
  styles/          # 全局样式、变量、设计令牌
  types/           # 通用类型定义
  utils/           # 纯工具函数
  App.vue
  main.ts
```

说明：

- 小项目可以先保留核心目录，不必一次性把所有目录建全
- `queries/` 不是 Vue 官方强制目录，但在存在服务端状态缓存时建议单独拆出
- 页面、组件、状态、接口、样式不要混放在同一层级

---

## 4. 职责边界

### 4.1 `pages/`

- 只放路由页面
- 负责页面级数据拼装、区域编排、路由参数处理
- 不承载大段可复用 UI 细节

### 4.2 `components/`

- 只放可复用界面组件
- 优先保持“输入 props，输出事件”的清晰边界
- 不直接承担页面级接口请求和路由页职责

### 4.3 `layouts/`

- 只处理页面骨架，例如顶部导航、侧栏、内容区容器
- 不耦合具体业务数据
- 布局应支持组合，而不是把页面逻辑写进布局中

### 4.4 `api/`

- 只负责 HTTP 请求封装、接口路径、请求参数、响应类型
- 不处理页面跳转、提示文案、组件状态
- 不承担缓存逻辑

### 4.5 `queries/`

- 只负责服务端状态查询、缓存、失效、轮询、重试等逻辑
- 列表、详情、分页、轮询等查询优先集中维护
- 不把服务端数据长期塞进 `stores/`

### 4.6 `stores/`

- 只放真正的客户端全局状态
- 例如登录态、主题、布局偏好、局部工作台状态
- 不把接口返回结果简单搬进 store 充当缓存

### 4.7 `composables/`

- 放可复用的组合式逻辑
- 适合封装表单逻辑、交互状态、滚动行为、局部视图逻辑
- 不应变成“什么都塞进去”的杂项目录

### 4.8 `utils/`

- 只放纯函数
- 不依赖组件实例、DOM 上下文或业务页面状态

---

## 5. 命名约定

- 组件文件：`PascalCase`，例如 `AppHeader.vue`
- 页面文件：`PascalCase + Page`，例如 `LoginPage.vue`
- 布局文件：`PascalCase + Layout`，例如 `WorkspaceLayout.vue`
- 组合函数：`useXxx.ts`，例如 `useVideoFilter.ts`
- Store：按领域命名，例如 `auth.ts`、`workspace.ts`
- API 文件：按领域命名，例如 `user.ts`、`video.ts`
- 工具函数文件：按能力命名，例如 `date.ts`、`format.ts`
- 样式类名保持语义化，不使用无含义缩写

---

## 6. 组件开发约束

- 默认使用单文件组件 `SFC`
- 默认使用 `<script setup lang="ts">`
- `props`、`emits`、暴露给模板的数据都应明确类型
- `v-for` 必须提供稳定 `key`
- 避免在同一节点上混用 `v-if` 和 `v-for`
- 公共组件优先保持无副作用，避免组件内部直接发起业务请求
- 复杂组件优先拆分，而不是在单个文件里堆积过多分支

---

## 7. 状态管理约束

- 组件内部临时状态优先使用 `ref` / `reactive`
- 页面共享但不需要全局持久化的逻辑，优先抽到 `composables`
- 客户端全局状态放 `stores`
- 服务端状态放 `queries`
- 不把“所有状态”都集中进 Pinia

一句话原则：

客户端状态归 `stores`，服务端状态归 `queries`，局部交互状态归组件或 `composables`。

---

## 8. 路由约束

- 路由页面只从 `pages/` 中引入
- 页面级鉴权、标题、权限信息建议收口到路由配置或 `meta`
- 在 Composition API 中统一使用 `useRoute()`、`useRouter()`
- 监听路由变化时，优先监听具体参数而不是整个路由对象
- 页面跳转逻辑放页面或组合函数中，不写进通用展示组件

---

## 9. 样式约束

- 全局样式只保留变量、重置、通用设计令牌和少量基础类
- 页面和组件样式优先局部化
- 不把大量页面样式堆进一个全局样式文件
- 样式命名优先体现结构和职责，不依赖纯视觉词
- 先保证结构清晰，再追加视觉修饰

---

## 10. 类型与接口约束

- TypeScript 项目中避免滥用 `any`
- 接口返回结构应有明确类型定义
- 通用类型放 `types/`，接口类型可按领域靠近 `api/`
- 复杂对象优先提取命名类型，不在组件中堆长内联类型

---

## 11. 开发与评审最低要求

- 开发前先明确本轮目标、范围、涉及文件、完成标准
- 大改前先确认布局骨架和硬约束，再开始实现
- 页面级大改按“小步提交、小 patch 修改”推进
- 评审不只看代码，必须看真实页面效果
- 至少执行一次构建校验
- 如项目已接入 lint、test、type-check，应与构建一起作为最低校验项

---

## 12. 不推荐的做法

- 把页面、接口、组件、状态逻辑全部堆在一个 `.vue` 文件中
- 把服务端查询结果长期塞入 Pinia 作为缓存
- 让公共组件直接承担路由页面职责
- 把布局组件写成具体业务页面
- 只凭代码阅读评审页面，不实际打开页面验证
- 目录名和文件名随意变化，缺乏统一命名规则

---

## 13. 一句话原则

先分层，再编码；先明确职责，再复用组件；先保证结构清晰，再做视觉和交互优化。
