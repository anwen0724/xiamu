<a id="module-goal"></a>
## 模块目标

前端模块用于承接“智看视频”已完成的后端 MVP 能力，面向在线学习者提供可用的 Web 端产品闭环，并在此基础上继续做体验优化和页面收口。

当前前端主闭环已经形成：

- 用户登录 / 注册
- 本地视频上传
- Dashboard 回访历史记录
- 统一视频详情页查看处理状态
- 成功后查看摘要、章节、转写内容
- 围绕结果创建和删除笔记

当前前端工作的重点不再是“把 MVP 首版做出来”，而是：

- 收敛首页设计和产品表达
- 优化统一详情页体验
- 稳定状态流与查询行为
- 统一全站页面宽度、布局和视觉语言

## 当前阶段判断

当前项目已经完成前后端 MVP 最小闭环，前端阶段判断如下：

- `frontend/` 工程已存在并可独立开发、构建
- 首页、登录、注册、Dashboard、统一详情页已经接通主流程
- 视频详情已从旧的“状态页 / 结果页”双页模式收敛为 `/video/:id` 单页模式

因此，本文件当前定位是“前端现状与迭代依据文档”，而不是“前端首版待启动规划文档”。

<a id="tech-stack"></a>
## 技术栈与工程组织

### 当前技术栈

- `Vue 3`
- `TypeScript`
- `Vite`
- `Vue Router`
- `Pinia`
- `Axios`
- `@tanstack/vue-query`

### 选择原因

- 当前前端工程已稳定运行在 `Vue 3 + Vite` 体系上，维护成本低
- 后端提供标准 REST 接口，且登录态基于 `HttpSession`，无需引入 SSR 或更重框架
- Dashboard、详情页、笔记等页面都属于典型数据驱动界面，`Pinia + Vue Query` 足以支撑

### 当前不采用的方案

- 不使用 `React`，避免维护者技术栈分裂
- 不使用 `Next.js` / `Nuxt`，当前没有 SSR、SEO 或服务端渲染需求
- 不引入大型后台 UI 框架作为主视觉基础，避免页面退化为通用管理后台

### 当前工程组织

当前前端工程位于仓库根目录下的 `frontend/`：

```text
frontend/
├─ src/
│  ├─ api/
│  ├─ components/
│  ├─ layouts/
│  ├─ pages/
│  │  ├─ auth/
│  │  ├─ dashboard/
│  │  ├─ home/
│  │  └─ video-detail/
│  ├─ queries/
│  ├─ router/
│  ├─ stores/
│  ├─ styles/
│  └─ utils/
├─ public/
└─ package.json
```

说明：

- `api/`：统一封装后端 REST 请求
- `queries/`：基于 `@tanstack/vue-query` 封装查询、缓存和失效策略
- `stores/`：只保留少量全局状态，例如当前登录用户
- `pages/`：按页面维度组织业务界面
- `layouts/` 与 `styles/`：承接全站布局和全局视觉变量

## 视觉与交互方向

前端视觉设计继续遵循“学习内容工作台”的方向，而不是泛后台模板。

推荐视觉关键词：

- 学习工作台
- 内容优先
- 目录索引感
- 批注与时间轴
- 安静
- 克制

执行原则：

- 首页和统一详情页要形成明显的产品记忆点
- 避免使用常见通用 SaaS 后台配色和后台模板式布局
- 详情页优先突出“摘要、章节、转写、笔记”的联动关系
- Dashboard 优先突出“继续学习”和“回访历史”
- 页面视觉统一应优先通过全局容器、颜色变量、卡片体系解决，而不是逐页打补丁

<a id="home-redesign"></a>
## 首页改版方案与当前落地

当前状态说明：

- 2026-03-26 已完成首页第一轮产品型改版实现
- 当前首页已经按“工具入口优先”的方向重构为：导航、Hero 上传区、能力速览、结果预览、使用场景、底部 CTA
- 本节以下内容继续保留，作为首页后续继续收口时的设计依据

### 改版背景

当前首页虽然已经完成上传入口、产品价值表达和首屏双栏结构，但整体视觉仍偏“展示型首页”，与当前希望靠近的“产品型工具首页”存在差异。

当前主要问题：

- 首屏设计表达强于工具入口，用户进入后先感知到“风格”，而不是先感知到“怎么开始”
- 标题与背景语言偏重，产品气质更像海报页，不够像成熟的 Web 工具首页
- 上传区虽然可用，但在整体叙事中的优先级仍可继续提升
- 场景区与说明区当前更像占位说明，产品化表达还不够扎实
- 移动端首屏信息密度和节奏仍可继续收紧

### 改版目标

- 将首页收敛为更偏产品型、工具型的首页，而不是概念展示页
- 首页首屏优先传达“这是一个上传学习视频并生成结果的工具”
- 保留当前已实现的真实能力，不展示未落地能力
- 建立一套更适合后续 Dashboard、详情页继续沿用的前端视觉基线

### 对标方向

本轮首页改版参考 `videoseek.ai`，但不直接复制其具体样式。

重点吸收的不是其紫蓝渐变，而是以下方法：

- 首屏以工具入口为中心，而不是以概念表达为中心
- 页面层级清楚，模块顺序稳定，用户能快速理解“做什么、怎么开始、有什么收益”
- 视觉采用浅色背景、白色卡片、统一圆角、轻阴影，整体更像成熟产品系统
- 文案更偏产品化和动作导向，而不是偏海报式口号表达

本项目不直接照搬的部分：

- URL 粘贴导入
- 多平台抓取能力展示
- 价格页、插件页、营销活动页相关表达
- 紫蓝渐变作为品牌主色

### 设计关键词

- 产品化
- 工具优先
- 学习工作台
- 清晰
- 安静
- 轻量
- 有秩序

### 视觉方向

首页视觉从“暖黄纹理 + 重标题”调整为“浅中性色背景 + 清爽主色 + 白卡片”方向。

主色不采用 `videoseek.ai` 的紫蓝渐变，建议改用更适合学习场景、耐看且稳定的青绿色体系：

- 主色：`#2F7F6D`
- 主色悬停：`#276B5C`
- 主色浅底：`#E4F1EC`
- 强调浅色：`#F3F8F6`
- 页面背景：`#F7F6F2`
- 卡片背景：`#FFFFFF`
- 主文字：`#1F2937`
- 次文字：`#667085`
- 边框色：`#E7E5E0`

### 首页信息架构

#### 1. 顶部导航

- 左侧：Logo + 产品名“智看视频”
- 右侧：登录、注册
- 如需强调主操作，可保留一个“开始上传”按钮

#### 2. 首屏 Hero

- 一句直接说明产品作用的标题
- 一句简短副标题，说明面向学习视频、处理结果和笔记入口
- 上传卡片作为首屏主要操作区
- 辅助说明上传格式、处理状态页和结果页去向

建议标题方向：

- 把学习视频整理成可读的学习结果
- 上传课程视频，快速得到摘要、章节和笔记入口

#### 3. 能力速览区

建议保留四张能力卡：

- 视频转写
- 智能摘要
- 章节导航
- 结果笔记

#### 4. 产品效果预览区

- 展示结果页预览图或拟真卡片
- 分三段说明“先读摘要 -> 再看章节 -> 最后记笔记”
- 让首页重点从“会上传”延伸到“上传之后有什么用”

#### 5. 使用场景区

建议保留以下场景：

- 网课复盘
- 知识分享整理
- 教学备课
- 个人学习回顾

要求：

- 四张卡片标题和说明都要区分开
- 不再使用相同描述反复复用

#### 6. 底部 CTA 区

- 一句短标题
- 一句补充说明
- 登录体验 / 注册账号 / 开始上传其中一到两个明确操作按钮

### 文案原则

- 少讲抽象概念，多讲用户动作和结果
- 少讲口号，多讲“上传后会得到什么”
- 一屏只传达一个重点
- 句子尽量短
- 不把首页写成 PRD，也不写成纯宣传海报

### 实现约束

- 只围绕当前已实现能力展开，不扩展 URL 导入、多平台抓取、价格体系等内容
- 首页继续保留真实上传入口，不做纯静态展示稿
- 新首页需要兼顾桌面端和移动端，移动端优先保证首屏节奏清楚、CTA 明确
- 改版时优先调整首页本身和相关全局视觉变量，不先把范围扩大到所有页面重做

### 完成标准

- 用户进入首页后能更快理解产品用途和入口
- 首页视觉重心明确落在“开始使用”而不是“风格表达”
- 整体气质更接近成熟产品首页，而不是概念海报页
- 设计风格与当前产品能力一致，不出现能力误导
- 能为后续 Dashboard 与详情页视觉统一提供基础

<a id="api-mapping"></a>
## 接口映射与前端约定

### 用户认证

- `POST /api/user/register`
- `POST /api/user/login`
- `POST /api/user/logout`
- `GET /api/user/get/login`

前端要求：

- 所有登录态请求统一带上凭证
- Axios 必须开启 `withCredentials`
- 启动时通过 `GET /api/user/get/login` 恢复当前登录用户

### 视频处理

- `POST /api/video/upload`
- `GET /api/video/status/{videoId}`
- `GET /api/video/status/stream/{videoId}`
- `GET /api/video/result/{videoId}`
- `GET /api/video/my/page`
- `POST /api/video/retry/{videoId}`

前端要求：

- 上传成功后直接进入统一详情页 `/video/:id`
- 详情页优先读取一次 `status` 快照，再订阅 SSE 状态流
- SSE 中断时允许回退到手动刷新或兜底重新拉取
- 只有在视频成功后才加载结果详情和笔记列表
- Dashboard 通过 `/my/page` 驱动

### 笔记

- `POST /api/note/add`
- `POST /api/note/update`
- `POST /api/note/delete`
- `GET /api/note/list/video`

前端要求：

- 笔记当前围绕统一详情页实现
- 笔记列表按视频维度拉取
- 新增、删除成功后局部刷新列表
- 后端已具备更新接口，但前端当前仍以新增、删除为主

<a id="state-design"></a>
## 前端状态设计

### 全局状态

建议由 `Pinia` 承载：

- 当前登录用户
- 认证初始化状态
- 少量全局 UI 状态

### 服务端状态

建议由 `Vue Query` 承载：

- Dashboard 列表
- 视频处理状态快照
- 视频结果详情
- 笔记列表

### 页面级临时状态

建议留在页面组件内部维护：

- SSE 连接状态
- 重试按钮提交态
- 笔记表单输入态
- 详情页局部页签或面板切换状态

约束：

- 不要把服务端查询结果重复塞进 Pinia
- 查询缓存、失效策略优先由 Query 管理
- SSE 推送结果用于触发详情页局部更新，不作为新的全局状态源

<a id="routing"></a>
## 当前路由规划

当前生效路由如下：

```text
/                    首页
/login               登录页
/register            注册页
/dashboard           Dashboard
/video/:id           统一视频详情页
/video/status/:id    兼容重定向到 /video/:id
/video/result/:id    兼容重定向到 /video/:id
```

路由规则：

- `/dashboard`、`/video/:id` 需要登录
- `/video/status/:id`、`/video/result/:id` 也受登录保护，但仅用于兼容旧链接
- 未登录访问受保护页面时，跳转 `/login`
- 登录后优先跳回原始目标页
- 已登录用户访问登录/注册页时，优先回到 `/dashboard`

<a id="known-constraints"></a>
## 当前已知约束

- 当前后端登录态采用 `HttpSession`，前端请求必须携带 Cookie
- 当前后端没有单独的播放器流媒体接口，详情页先不做复杂播放器能力
- 当前章节质量允许存在降级情况，前端必须兼容“摘要存在但章节为空”的场景
- 当前结果页接口返回聚合结果对象，前端应优先直接消费，不自行拼装后端实体
- 后端视频 ID 使用雪花 `Long`，前端必须统一按字符串处理，避免 JavaScript 精度丢失
- 详情页宽度和留白当前仍受全局容器策略影响，页面优化时要优先改全局而不是单页补丁

<a id="current-focus"></a>
## 当前迭代重点

当前前端迭代重点建议按以下顺序推进：

1. 首页改版，收敛为更明确的产品型工具首页

3. 补齐详情页内未完成的交互，例如更完整的笔记编辑与内容消费体验
4. 继续优化状态流稳定性、查询策略和异常处理

### 2026-03-25（联调修正）

本次修正内容：

- 修正前端对后端雪花 `Long` ID 的处理方式
- 将前端涉及后端实体的 `id` 类型统一改为字符串，避免 JavaScript `number` 精度丢失
- 状态页和结果页路由参数不再做 `Number()` 转换，统一按字符串透传
- 收敛查询策略：
  - Dashboard 列表增加 `staleTime`
  - 关闭窗口聚焦自动重查
  - 关闭错误重试
  - 状态页在请求报错时停止轮询

问题原因：

- 后端视频 ID 使用雪花 `Long`，数值超过 JavaScript 安全整数范围
- 前端先前按 `number` 接收视频 ID，导致上传成功后跳转到错误的 `videoId`
- 状态页因此请求了错误的 `/api/video/status/{videoId}`，后端返回“视频不存在”
- 同时状态页原有轮询逻辑在报错场景下仍继续轮询，导致错误请求持续打到后端

涉及文件：

- `frontend/src/api/types.ts`
- `frontend/src/api/video.ts`
- `frontend/src/api/note.ts`
- `frontend/src/queries/video.ts`

- `frontend/src/pages/dashboard/DashboardPage.vue`
- `frontend/src/pages/video-status/VideoStatusPage.vue`

本次结果：

- 上传后状态页与结果页链路不再因雪花 ID 精度丢失而访问错误视频

### 2026-03-26 更新：结果详情页布局调整复盘

### 本次确认的已实现内容

- 统一详情页路由继续使用 `/video/:id`
- 左侧已按“播放区 + 下方内容区”的结构接入两组小导航：`语音转文本`、`原始字幕`
- 右侧已接入三组页签：`总结`、`思维导图`、`备忘录`
- 统一详情页继续保留前一轮已完成的状态流能力：状态快照查询、SSE 推送、失败重试、笔记增删

### 本次讨论确认的问题根因

- 站点整体内容宽度主要由全局样式控制，而不是单个页面单独决定
- 当前全站主容器宽度定义在 `frontend/src/styles/main.css`：`--page-max-width` 与 `.page-shell`
- 由于 `.page-shell` 默认使用 `margin: 0 auto` 且受 `--page-max-width` 限制，页面在大屏下会自然形成“中间内容区 + 两侧留白”的布局
- 结果详情页没有完全跟随全局宽度放开，是因为调试中额外引入了 `AppLayout` 的 `wide` 模式，形成了第二层宽度限制
- 因此，“结果页为什么还是挤在中间”的根因不是单一页面组件本身，而是“全局容器宽度策略 + 结果页额外叠加的局部宽度策略”共同作用

### 本次确认的定位结论

- 如果要调整整个站点的页面宽度，应优先修改全局容器策略，而不是逐页打补丁
- 如果只改结果页，需要同时检查两层：
  - 全局 `.page-shell`
  - `AppLayout` 或结果页自身额外增加的宽度限制
- 本次调试过程中新增的 `AppLayout wide` 属于单页绕开式方案，不应作为长期的全站布局方案

### 建议的后续处理方向

- 先统一全站的页面容器宽度策略
- 再单独微调结果页的左右栏比例、顶部工具条和字幕列表密度
- 不再继续叠加“单页专用最大宽度”这类临时补丁，避免后续页面行为不一致
