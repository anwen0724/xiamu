# 前端模块开发文档

## 模块目标

前端模块用于承接“智看视频”MVP 已完成的后端能力，面向在线学习者提供可用的 Web 端产品闭环。

本模块不追求首版即覆盖全部长期规划，而是优先完成以下最小闭环：

- 用户登录 / 注册
- 本地视频上传
- 处理状态查看
- 结果页查看摘要与章节
- 围绕结果创建和查看笔记
- Dashboard 回访历史处理记录

## 产品与范围约束

本模块的实现边界以以下文档为准：

- `docs/00-PRD.md`
- `docs/01-实现前决策清单.md`
- `docs/02-MVP开发说明.md`

当前前端必须遵守的范围约束：

- 目标用户：在线学习者
- 产品形态：Web 网页应用
- MVP 只做本地上传，不做 URL 导入
- MVP 只做首页、登录、注册、Dashboard、状态页、结果页
- 笔记能力先嵌入结果页，不先独立做完整“笔记中心”
- 知识库、测试题、学习计划、多人协作、社区分享不进入当前阶段

## 技术选型

### 当前确定方案

前端技术栈统一确定为：

- `Vue 3`
- `TypeScript`
- `Vite`
- `Vue Router`
- `Pinia`
- `Axios`
- `@tanstack/vue-query`
- `CSS Modules` 或 `SCSS Modules`

### 选择原因

- 当前仓库没有现成前端工程，采用 `Vite + Vue 3` 启动成本最低
- 项目后续主要维护者更熟悉 Vue，优先保证可维护性
- 当前后端提供的是标准 REST 接口，且登录态基于 `HttpSession`，无需引入 SSR 或更重的前端框架
- 结果页、状态页、Dashboard 都属于典型数据驱动页面，`Pinia + Vue Query` 足以支撑

### 当前不采用的方案

- 不使用 `React`，避免维护者技术栈分裂
- 不使用 `Next.js` / `Nuxt`，当前没有 SSR、SEO 或服务端渲染需求
- 不引入大型后台 UI 框架作为主视觉基础，避免页面直接退化为通用管理后台

## 视觉与交互方向

本模块的视觉设计遵循 `frontend-design` skill 的方向，但要结合当前产品定位收敛为“学习内容工作台”，而不是泛后台模板。

推荐视觉关键词：

- 编辑感
- 学习档案感
- 目录索引感
- 批注与时间轴
- 内容优先

执行原则：

- 首页和结果页要形成明显的产品记忆点
- 避免使用常见通用 SaaS 后台配色和排版
- 结果页优先突出“摘要、章节、笔记”的联动关系
- Dashboard 优先突出“继续学习”和“回访历史”，而不是管理操作

## 页面与接口映射

### 用户认证

- `POST /api/user/register`
- `POST /api/user/login`
- `POST /api/user/logout`
- `GET /api/user/get/login`

前端要求：

- 所有登录态请求统一带上凭证
- Axios 必须开启 `withCredentials`
- 启动时通过 `GET /api/user/get/login` 恢复当前登录用户

### 视频处理

- `POST /api/video/upload`
- `GET /api/video/status/{videoId}`
- `GET /api/video/result/{videoId}`
- `GET /api/video/my/page`
- `POST /api/video/retry/{videoId}`

前端要求：

- 上传成功后优先进入状态页
- 状态页轮询 `/status/{videoId}`
- 当状态满足可展示条件时跳转结果页
- Dashboard 通过 `/my/page` 驱动

### 笔记

- `POST /api/note/add`
- `POST /api/note/update`
- `POST /api/note/delete`
- `GET /api/note/list/video`

前端要求：

- 笔记先围绕结果页实现
- 笔记列表按视频维度拉取
- 添加、编辑、删除成功后局部刷新列表

## 前端状态设计

### 全局状态

建议由 `Pinia` 承载：

- 当前登录用户
- 认证初始化状态
- 全局上传弹层 / 页面级 UI 状态（如需要）

### 服务端状态

建议由 `Vue Query` 承载：

- Dashboard 列表
- 视频结果详情
- 视频处理状态
- 笔记列表

约束：

- 不要把服务端查询结果重复塞进 Pinia
- 轮询、缓存、失效策略优先由 Query 管理

## 路由规划

推荐首版路由如下：

```text
/                    首页
/login               登录页
/register            注册页
/dashboard           Dashboard
/video/status/:id    处理状态页
/video/result/:id    结果详情页
```

路由规则：

- `/dashboard`、`/video/status/:id`、`/video/result/:id` 需要登录
- 未登录访问受保护页面时，跳转 `/login`
- 登录后优先跳回原始目标页

## 工程目录建议

建议前端工程放在仓库根目录下的 `frontend/`：

```text
frontend/
├─ src/
│  ├─ router/
│  ├─ layouts/
│  ├─ pages/
│  │  ├─ home/
│  │  ├─ auth/
│  │  ├─ dashboard/
│  │  ├─ video-status/
│  │  └─ video-result/
│  ├─ components/
│  ├─ stores/
│  ├─ api/
│  ├─ queries/
│  ├─ composables/
│  ├─ utils/
│  └─ styles/
├─ public/
└─ package.json
```

目录说明：

- `api/`：统一封装后端 REST 请求，例如 `user.ts`、`video.ts`、`note.ts`
- `queries/`：基于 `@tanstack/vue-query` 封装查询、轮询和缓存策略
- `composables/`：Vue 组合式逻辑复用层，例如认证恢复、上传交互、结果页联动
- `stores/`：只存少量全局状态，如当前登录用户和局部 UI 状态

## 当前已知约束

- 当前后端登录态采用 `HttpSession`，前端请求必须携带 Cookie
- 当前后端没有单独的播放器流媒体接口，结果页先不做复杂播放器能力
- 当前章节质量允许存在降级情况，前端必须兼容“摘要存在但章节为空”的场景
- 当前结果页接口返回的是聚合结果对象，前端应优先直接消费，不自行拼装后端实体

## 后续计划

- 在前端正式启动开发时，先建 `frontend/` 工程
- 第一轮只实现页面骨架和接口联调，不先做播放器增强

### 2026-03-25（联调修正）

本次修正内容：

- 修正前端对后端雪花 `Long` ID 的处理方式
- 将前端涉及后端实体的 `id` 类型统一改为字符串，避免 JavaScript `number` 精度丢失
- 状态页和结果页路由参数不再做 `Number()` 转换，统一按字符串透传
- 收敛查询策略：
  - Dashboard 列表增加 `staleTime`
  - 关闭窗口聚焦自动重查
  - 关闭错误重试
  - 状态页在请求报错时停止轮询

问题原因：

- 后端视频 ID 使用雪花 `Long`，数值超过 JavaScript 安全整数范围
- 前端先前按 `number` 接收视频 ID，导致上传成功后跳转到错误的 `videoId`
- 状态页因此请求了错误的 `/api/video/status/{videoId}`，后端返回“视频不存在”
- 同时状态页原有轮询逻辑在报错场景下仍继续轮询，导致错误请求持续打到后端

涉及文件：

- `frontend/src/api/types.ts`
- `frontend/src/api/video.ts`
- `frontend/src/api/note.ts`
- `frontend/src/queries/video.ts`
- `frontend/src/queries/note.ts`
- `frontend/src/pages/dashboard/DashboardPage.vue`
- `frontend/src/pages/video-status/VideoStatusPage.vue`
- `frontend/src/pages/video-result/VideoResultPage.vue`

本次结果：

- 上传后状态页与结果页链路不再因雪花 ID 精度丢失而访问错误视频
- 后端“视频不存在”异常不再由前端错误 `videoId` 触发
- Dashboard 与状态页的重复查询压力已明显收敛
