# 智看视频 MVP 开发任务拆解

## 1. 文档目标

本文档将 MVP 范围拆成可执行的开发任务，按依赖关系排序，明确每一阶段要交付什么、依赖什么、完成标准是什么，便于连续推进。

## 2. 总体开发顺序

1. 补齐结果链路
2. 补齐结果查询接口
3. 补齐用户系统
4. 补齐笔记模块
5. 补齐 Dashboard
6. 补齐工程保障能力

当前项目已完成上传、音频提取、转写，因此下一阶段的重心应放在“让用户看到结果并使用结果”。

## 3. Phase 3：AI 内容生成

### 任务 3.1：定义摘要与章节输出结构

- 目标：统一摘要、章节在数据库和接口中的存储格式
- 产出：`summary` 文本结构约定，`chapters` JSON 结构约定
- 依赖：现有 `video` 表已预留字段
- 完成标准：文档与代码中都能稳定读写同一结构

### 任务 3.2：实现摘要生成服务

- 目标：基于 `transcript` 生成可读摘要
- 产出：摘要生成 Service、调用链路、错误处理
- 依赖：转写结果已落库
- 完成标准：处理完成后 `summary` 字段有有效内容

### 任务 3.3：实现章节与时间戳生成服务

- 目标：从转写文本或分段结果中生成章节标题与时间区间
- 产出：章节生成 Service、章节 JSON 落库逻辑
- 依赖：Whisper 分段结果可用，或可从文本二次加工
- 完成标准：`chapters` 字段可生成前端可展示的数据

### 任务 3.4：补齐最终状态流转

- 目标：让处理链路真正进入最终完成态
- 产出：`SUCCESS`、降级成功、失败的统一判定逻辑
- 依赖：摘要和章节生成逻辑完成
- 完成标准：处理链路结束后状态明确，不再停留在中间态 `WAITING`

## 4. Phase 4：结果页接口

### 任务 4.1：提供视频结果查询接口

- 目标：按视频 ID 查询详情
- 产出：结果页详情接口
- 依赖：摘要、章节、转写结果已可读取
- 完成标准：接口能返回视频基础信息、状态、摘要、章节、错误信息

### 任务 4.2：提供处理状态查询接口

- 目标：前端可轮询处理状态
- 产出：状态查询接口
- 依赖：状态设计已稳定
- 完成标准：前端可明确区分等待中、处理中、成功、失败

### 任务 4.3：统一结果页返回对象

- 目标：避免直接暴露数据库实体
- 产出：结果页专用 VO / DTO
- 依赖：结果字段结构明确
- 完成标准：接口返回字段稳定，便于前端直接消费

## 5. Phase 5：用户系统

### 任务 5.1：设计用户表与基础认证模型

- 目标：建立最小用户体系
- 产出：`user` 表、实体、Mapper、Service
- 依赖：无
- 完成标准：可存储账号、密码、昵称等基础字段

### 任务 5.2：实现注册与登录接口

- 目标：支持基础账号体系
- 产出：注册接口、登录接口、登录态方案
- 依赖：用户表已建立
- 完成标准：用户可完成注册登录并保持登录状态

### 任务 5.3：接通业务数据归属

- 目标：将视频、笔记与用户关联
- 产出：上传视频时写入 `userId`，查询时按用户隔离
- 依赖：用户认证完成
- 完成标准：用户只能访问自己的视频和笔记

## 6. Phase 6：基础笔记模块

### 任务 6.1：设计笔记表与数据模型

- 目标：支持围绕视频记笔记
- 产出：`note` 表、实体、Mapper、Service
- 依赖：用户系统完成
- 完成标准：支持 `userId`、`videoId`、标题、内容、时间戳等核心字段

### 任务 6.2：实现笔记增删改查接口

- 目标：提供最基础的笔记能力
- 产出：创建、编辑、删除、查询接口
- 依赖：笔记表完成
- 完成标准：用户可围绕视频创建与维护笔记

### 任务 6.3：实现笔记与视频结果页联动

- 目标：让用户在看结果时立即开始记笔记
- 产出：按视频查询笔记、按视频创建笔记的接口能力
- 依赖：结果页与笔记接口已存在
- 完成标准：结果页具备笔记入口，后端数据结构已支撑联动

## 7. Phase 7：Dashboard

### 任务 7.1：实现历史视频列表接口

- 目标：展示最近处理过的视频
- 产出：分页列表接口
- 依赖：用户体系完成
- 完成标准：返回标题、状态、时长、创建时间、快捷入口信息

### 任务 7.2：实现列表筛选与排序

- 目标：让 Dashboard 基本可用
- 产出：按状态、时间排序的查询参数
- 依赖：历史列表接口完成
- 完成标准：前端可按常见条件组织列表展示

## 8. Phase 8：工程保障与收尾

### 任务 8.1：补齐文件生命周期管理

- 目标：避免本地存储持续膨胀
- 产出：原视频、音频的清理策略与任务
- 依赖：文件保留规则已确定
- 完成标准：可按规则自动清理临时或过期文件

### 任务 8.2：补齐失败重试机制

- 目标：提高处理链路稳定性
- 产出：转写失败、AI 生成失败的重试能力
- 依赖：状态流转已稳定
- 完成标准：失败场景可重试，且不会污染最终状态

### 任务 8.3：补齐基础测试

- 目标：降低后续迭代风险
- 产出：服务层、接口层、关键工具类测试
- 依赖：主要功能完成
- 完成标准：关键链路具备最基本自动化验证

### 任务 8.4：补齐运行文档

- 目标：保证项目可复现运行
- 产出：环境依赖、启动步骤、FFmpeg / Python / Whisper 配置说明
- 依赖：核心能力稳定
- 完成标准：新环境可按文档完成运行

## 9. 推荐执行顺序

最推荐的实际推进顺序如下：

1. 先做摘要生成
2. 再做章节生成
3. 然后补结果详情接口与状态查询接口
4. 之后做用户系统
5. 再做基础笔记
6. 最后做 Dashboard、清理策略、重试和测试

这样安排的原因是，MVP 当前最大的缺口不是“缺更多模块”，而是“已有处理链路还没有形成用户能看见的结果闭环”。

## 10. 每阶段完成定义

- Phase 3 完成：处理链路可产出摘要和章节，并进入最终完成态
- Phase 4 完成：前端已有足够接口展示结果页
- Phase 5 完成：用户数据开始真正归属到个人账号
- Phase 6 完成：用户可以围绕视频创建和维护笔记
- Phase 7 完成：用户可以回访历史视频
- Phase 8 完成：系统具备最基本可维护性与可持续运行能力

## 11. 当前最优先的三个任务

- 任务一：定义并实现摘要生成链路
- 任务二：定义并实现章节生成链路
- 任务三：提供结果详情和状态查询接口

这三个任务完成后，项目就会从“处理管道已存在”升级为“用户可以实际消费处理结果”，这是当前 MVP 最关键的跨越。
