# AI 多模型路由改造记录

## 1. 本次目标

本次改造的目标不是实现主备模型自动切换，而是将当前单模型接入方式升级为“多模型可配置、可路由、可按任务选择”的结构，便于后续在 OpenAI、DeepSeek 等多个 OpenAI-compatible 模型之间切换和扩展。

## 2. 改造背景

在改造前，项目中的 AI 能力存在以下特点：

- 摘要和章节服务都直接注入 Spring 自动装配的默认 `ChatClient.Builder`
- 模型选择完全依赖 `spring.ai.openai.chat.options.model`
- 项目层面只能天然使用一个默认模型
- 若要切换到其它模型，需要直接修改默认配置，无法同时保留多个模型定义

这种结构适合单模型场景，但不适合“同时配置多个模型，并可能按场景选择不同模型使用”的后续需求。

## 3. 最终方案

本次采用的方案是：

- 单一 AI 配置入口
- 多模型客户端装配
- AI 模型路由器
- 业务服务按任务类型路由模型
- 可选显式 `modelKey`

整体结构如下：

`application.yml -> AiProperties -> OpenAiModelConfig / DeepSeekModelConfig -> AiModelRegistry -> AiModelRouter -> AiSummaryService / AiChapterService`

## 4. 核心设计

### 4.1 多模型配置

当前配置入口统一放在 `xiamu.ai` 下，主要包含：

- `default-model`
- `summary-model`
- `chapter-model`
- `models`

其中 `models` 下面每个 key 表示一个可用模型实例，例如：

- `openai`
- `deepseek`

每个模型实例包含：

- `provider`
- `api-key`
- `base-url`
- `model`
- `temperature`
- `enabled`

### 4.2 客户端装配

当前客户端装配拆成两个 provider 配置类：

- `OpenAiModelConfig`
- `DeepSeekModelConfig`

它们的职责是：

- 从 `AiProperties.models` 中筛选出属于当前 provider 的模型配置
- 为每个模型实例创建对应的 `ChatClient`
- 将每个模型实例装配为 `AiModelRegistration`
- 最终输出为 `AiModelRegistry.RegistrationGroup`

这样做的好处是：

- provider 相关的实例化细节只留在 `config` 层
- `routing` 层只处理“有哪些模型可用”和“这次该选哪个”
- `service` 层不需要知道底层到底是 OpenAI 还是 DeepSeek

### 4.3 路由器

路由器由 `AiModelRouter` 负责，职责是：

- 根据任务类型决定默认用哪个模型
- 当显式传入 `modelKey` 时优先使用显式模型
- 对路由结果打日志

当前路由结构分为两层：

- `AiModelRegistry`：负责收集和校验所有已注册模型
- `AiModelRouter`：负责按任务类型或显式 `modelKey` 选择本次实际使用的模型

这样拆分后：

- 注册职责和路由职责分开
- 如果后续增加更多 provider，不需要改业务服务
- 如果后续增加 fallback 或灰度逻辑，可以继续在 `AiModelRouter` 上扩展

当前支持的任务类型有：

- `SUMMARY`
- `CHAPTER`

路由优先级为：

1. 显式传入的 `modelKey`
2. 任务类型默认模型配置
3. 全局默认模型

### 4.4 业务服务

摘要服务和章节服务仍然保留原有业务职责：

- 负责 Prompt
- 负责结果校验
- 负责内容解析

改造后，它们不再依赖一个固定的默认 `ChatClient.Builder`，而是通过 `AiModelRouter` 获取当前要用的模型注册信息，再从中取得对应 `ChatClient`。

为了兼容现有调用方式，两个服务都保留了原始方法，同时新增显式模型调用重载：

- `generateSummary(String transcript)`
- `generateSummary(String transcript, String modelKey)`
- `generateChapters(String transcript, String transcriptionJson, Long durationSeconds)`
- `generateChapters(String transcript, String transcriptionJson, Long durationSeconds, String modelKey)`

## 5. 当前配置示例

当前项目中的配置方式如下：

```yaml
xiamu:
  ai:
    default-model: openai
    summary-model: ${AI_SUMMARY_MODEL:}
    chapter-model: ${AI_CHAPTER_MODEL:}
    models:
      openai:
        enabled: true
        provider: openai
        api-key: ${OPENAI_API_KEY:}
        base-url: ${OPENAI_BASE_URL:https://api.openai.com}
        model: ${OPENAI_MODEL:gpt-4.1-mini}
        temperature: 0.3
      deepseek:
        enabled: true
        provider: deepseek
        api-key: ${DEEPSEEK_API_KEY:}
        base-url: ${DEEPSEEK_BASE_URL:https://api.deepseek.com}
        model: ${DEEPSEEK_MODEL:deepseek-chat}
        temperature: 0.3
```

## 6. 当前使用方式

### 6.1 默认路由

如果业务代码不显式传入 `modelKey`，则：

- 摘要任务优先使用 `xiamu.ai.summary-model`
- 章节任务优先使用 `xiamu.ai.chapter-model`
- 如果任务模型未配置，则回退到 `xiamu.ai.default-model`

### 6.2 显式指定模型

如果后续某段业务想直接指定模型，可调用带 `modelKey` 的重载方法，例如：

```java
aiSummaryService.generateSummary(transcript, "deepseek");
```

或：

```java
aiChapterService.generateChapters(transcript, transcriptionJson, durationSeconds, "openai");
```

## 7. 为什么没有做主备自动切换

本次明确没有引入主备自动切换，原因如下：

- 当前诉求是“方便配置多个模型并自行切换”，而不是“某个模型失败时自动兜底”
- 自动 fallback 会让日志、调试和调用成本管理变复杂
- 当前阶段先完成“多模型可注册、可路由、可显式选择”更符合实际使用场景

如后续确实需要主备能力，可以在当前 `AiModelRouter` 之上继续扩展 fallback 规则，而无需推翻本次结构。

## 9. 当前结论

本次改造后，项目已经从“单默认模型接入”升级为“统一配置 + 多模型装配 + 路由选择”结构。  
这为后续扩展以下能力打下了基础：

- 接入更多 OpenAI-compatible 模型
- 让不同任务使用不同默认模型
- 在部分业务场景中显式指定模型
- 后续按需扩展主备切换、A/B 或灰度路由

## 10. DeepSeek 接入说明补充

当前代码中的 DeepSeekModelConfig 已调整为通过 OpenAI-compatible 方式接入，而不是直接依赖 spring-ai-deepseek。

本次这样处理的原因是：

- 当前项目依赖栈仍是 Spring Boot 3.2.5
- 本地开发环境未成功解析 spring-ai-deepseek
- 为了先保持多模型路由结构可用，同时避免阻塞整体开发，暂时统一复用 OpenAiApi + OpenAiChatModel 这套兼容实现

这意味着当前：

- provider=openai 走 OpenAI 官方接口
- provider=deepseek 走 DeepSeek 的 OpenAI-compatible 接口

后续如果项目升级 Spring AI / Spring Boot 依赖栈，并确认仓库可稳定解析 spring-ai-deepseek，可再切回 provider 原生实现。

## 11. 详细执行流程说明

下面按“配置加载 -> 模型装配 -> 模型注册 -> 模型路由 -> 业务调用”顺序说明当前完整流程。

### 11.1 第一步：读取配置

系统启动时，`AiProperties` 会读取 `application.yml` 中的 `xiamu.ai` 配置，主要包括：

- `default-model`
- `summary-model`
- `chapter-model`
- `models.<key>`

其中 `models.<key>` 表示一个具体模型实例，例如：

- `openai`
- `deepseek`

此时系统只是把配置读进内存，还没有真正创建模型客户端。

### 11.2 第二步：按 provider 装配模型客户端

启动阶段会进入两个配置类：

- `OpenAiModelConfig`
- `DeepSeekModelConfig`

它们分别做这些事情：

1. 遍历 `AiProperties.models`
2. 只处理自己负责的 provider
3. 根据该模型的 `api-key / base-url / model / temperature` 创建 `ChatClient`
4. 组装成 `AiModelRegistration`

当前的差异是：

- `OpenAI` 直接走 OpenAI 接口
- `DeepSeek` 当前也复用 `OpenAiApi + OpenAiChatModel`，但 `base-url` 指向 `https://api.deepseek.com`

也就是说，当前 `deepseek` 在代码结构上是独立 provider，在底层协议实现上是 `OpenAI-compatible`。

### 11.3 第三步：汇总到模型注册表

两个 provider 配置类最终会各自产出一个 `AiModelRegistry.RegistrationGroup`，随后由 `AiModelRegistry` 统一收集。

`AiModelRegistry` 负责：

- 合并多个 provider 下的模型
- 检查模型 key 是否重复
- 对外提供：
  - `getRequired(modelKey)`
  - `getDefault(defaultModelKey)`

这一层解决的是“系统里当前到底有哪些模型可用”。

### 11.4 第四步：路由器决定本次使用哪个模型

当业务层发起摘要或章节请求时，会进入 `AiModelRouter`。

`AiModelRouter` 的选择顺序是：

1. 如果调用方显式传了 `modelKey`，直接用这个
2. 如果没有显式传参，则按任务类型取默认模型
   - `SUMMARY -> summary-model`
   - `CHAPTER -> chapter-model`
3. 如果任务默认模型也没配，就回退到 `default-model`

这一层解决的是“这次调用具体用哪个模型”。

### 11.5 第五步：业务服务发起实际模型调用

业务服务层包括：

- `AiSummaryServiceImpl`
- `AiChapterServiceImpl`

它们只负责：

- 组装 Prompt
- 调 `AiModelRouter` 选模型
- 调用对应 `ChatClient`
- 解析结果
- 做结果校验

也就是说：

- `service` 不负责模型实例化
- `routing` 不负责 Prompt
- `config` 不负责业务语义

这就是当前结构清晰的关键。

## 12. 简单调用实例

下面用“显式指定 DeepSeek 生成摘要”举一个最小调用例子。

### 12.1 配置

```yaml
xiamu:
  ai:
    default-model: openai
    models:
      openai:
        enabled: true
        provider: openai
        api-key: ${OPENAI_API_KEY:}
        base-url: ${OPENAI_BASE_URL:https://api.openai.com}
        model: ${OPENAI_MODEL:gpt-4.1-mini}
        temperature: 0.3
      deepseek:
        enabled: true
        provider: deepseek
        api-key: ${DEEPSEEK_API_KEY:}
        base-url: ${DEEPSEEK_BASE_URL:https://api.deepseek.com}
        model: ${DEEPSEEK_MODEL:deepseek-chat}
        temperature: 0.3
```

### 12.2 业务代码调用

```java
String summary = aiSummaryService.generateSummary(
        transcript,
        "deepseek"
);
```

### 12.3 内部执行过程

这段代码在内部会按下面顺序执行：

1. `AiSummaryServiceImpl` 接收到 `transcript` 和 `modelKey=deepseek`
2. `AiSummaryServiceImpl` 先规范化、截断转写文本
3. 调用 `AiModelRouter.route(AiTaskType.SUMMARY, "deepseek")`
4. `AiModelRouter` 发现有显式 `modelKey`，直接选择 `deepseek`
5. `AiModelRegistry` 返回 `deepseek` 对应的 `AiModelRegistration`
6. `AiSummaryServiceImpl` 从注册信息中拿到 `ChatClient`
7. 通过 `ChatClient.prompt().system(...).user(...).call().content()` 发起请求
8. 底层实际走到 `DeepSeekModelConfig` 装配好的 OpenAI-compatible 客户端
9. 返回摘要字符串

### 12.4 如果不显式传 `modelKey`

如果你这样调用：

```java
String summary = aiSummaryService.generateSummary(transcript);
```

那么流程会变成：

1. `AiModelRouter` 先看 `summary-model`
2. 如果 `summary-model` 没配，再看 `default-model`
3. 最终选出当前摘要任务的默认模型

因此你可以把当前系统理解成两种使用方式：

- 日常默认调用：让路由器按配置自动选模型
- 特殊场景调用：显式传 `modelKey` 精准指定模型

## 13. 章节兜底与降级说明

在当前实现中，章节生成比摘要生成更容易受到短视频、短文本和模型输出格式波动的影响，因此补充了两层保护：

### 13.1 短视频单章节兜底

当满足以下任一条件时，系统会把当前视频视为短视频场景：

- 转写文本较短
- 视频时长较短

如果此时模型返回的章节结果出现以下问题：

- 未找到 JSON 数组
- JSON 无法解析
- 章节全部被后置校验过滤

系统会自动兜底生成一个单章节结果，例如：

```json
[
  {
    "title": "完整内容",
    "startSeconds": 0,
    "endSeconds": 67,
    "summary": "这是一个很短的视频测试文本"
  }
]
```

### 13.2 章节失败不拖累摘要

在 `WhisperTranscriptionServiceImpl` 中，当前处理顺序是：

1. 先转写
2. 再生成摘要
3. 再生成章节

现在即使章节生成失败：

- 只要摘要成功，视频最终仍会进入 `SUCCESS`
- `summary` 会正常保留
- `chapters` 会降级写成 `[]`

这样做的原因是：

- 摘要已经是可消费结果
- 章节失败不应让整条处理链完全失效
- 章节问题应通过日志继续排查，而不是直接丢弃已经成功的摘要
