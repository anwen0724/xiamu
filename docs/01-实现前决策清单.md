# 智看视频 - 实现前决策清单

## 文档目的

这份清单不是补充功能列表，而是用于在正式实现前，先把最关键的产品和工程约束定下来。

如果这几个问题不先回答，项目很容易出现以下问题：

- 功能范围持续膨胀，MVP 失焦
- 技术实现已经开始，但上线条件仍不明确
- 处理链路可运行，但用户拿到的结果不稳定、不可信
- 成本、版权、时延问题在开发后期集中暴露

---

## 一、MVP 到底服务谁，解决什么刚需

### 要回答的问题

第一版产品到底只服务哪一类用户？在什么场景下，用户愿意放弃现有替代方案，转而使用“智看视频”？

### 当前 PRD 的问题

当前 PRD 同时覆盖了两类不同用户：

- 内容消费者：看播客、访谈、长视频，想快速抓重点
- 在线学习者：看教程、网课、编程视频，想提高学习效率

这两类用户有重叠，但核心诉求不同：

- 内容消费者更在意“快速摘要、章节跳转、信息回顾”
- 在线学习者更在意“笔记、知识沉淀、测试题、学习计划”

如果第一版同时满足两类人，产品、交互、数据结构、评估指标都会分散。

### 推荐答案

推荐把第一版用户收敛为：

**看教程/课程/技术分享视频的在线学习者**

推荐把第一版核心场景定义为：

**用户上传一个 30 分钟到 2 小时的学习类视频，系统在可接受时间内生成结构化摘要和可跳转章节，帮助用户快速定位重点并开始记笔记。**

### 为什么推荐这样收敛

- 学习场景比泛内容消费场景更容易形成复用和留存
- “摘要 + 章节 + 笔记”链路天然连贯，产品闭环更清晰
- 后续扩展到知识库、测试题、学习计划也更自然
- 相比“播客/访谈速览”，学习场景更能容忍一定识别误差

### 不建议第一版同时做的事情

- 同时兼顾“播客速览工具”和“学习辅助工具”
- 一开始就做社区分享、多用户协作
- 一开始就做 AI 测试题、学习计划、知识卡片的完整闭环

### 建议直接定下来的结论

- 第一版目标用户：在线学习者
- 第一版目标内容：教程、课程、知识分享类视频
- 第一版核心价值：快速理解 + 快速定位 + 快速开始记笔记
- 第一版北极星动作：用户处理完一个视频后，进入摘要页并点击章节或创建笔记

## 二、视频来源、版权边界、成本边界是什么

### 要回答的问题

第一版到底支持哪些视频来源？单个用户能处理多大、多长的视频？系统保存哪些文件、多长时间？哪些行为有版权和成本风险？

### 当前 PRD 的问题

当前 PRD 中以下关键约束仍未收紧：

- URL 导入支持哪些平台，未定
- 文件大小限制，未定
- 视频时长限制，未定
- 文件存储方案，未定
- 视频处理后保留多久，未定
- 版权风险只被识别，但未转化为产品规则

这些问题如果不先定，后端虽然可以继续开发，但实际运行时会马上遇到问题：

- 磁盘占用不可控
- 处理队列被超长视频拖垮
- URL 导入带来平台兼容和版权问题
- Whisper 和后续 AI 分析成本失控

### 推荐答案

推荐第一版采用以下边界：

- 只支持**本地上传**
- 暂不开放**URL 导入**
- 只支持常见格式：`mp4`
- 单文件上限：`1GB`
- 单视频时长上限：`2 小时`
- 视频文件默认保留 `7 天`
- 提取后的音频文件默认保留 `24 小时`
- 转写文本、摘要、章节结果长期保留
- 每个用户先不做复杂套餐，但需要有基础限流，例如每日处理次数上限

### 为什么推荐先砍掉 URL 导入

- 技术复杂度明显更高，需要处理下载失败、平台差异、反爬限制、格式兼容
- 版权风险更高，特别是第三方平台内容
- 这不是验证核心价值所必需的能力
- 本地上传已经足够验证“处理链路是否成立”

### 为什么要尽早写清楚留存策略

这是工程问题，也是产品规则问题：

- 原始视频最占磁盘
- 音频是中间产物，通常不需要长期留存
- 文本和结构化结果体积小，适合保留
- 用户删除视频时，是否联动删除源文件和音频，也需要规则先行

### 建议直接定下来的结论

- 第一版只做本地上传，不做 URL 导入
- 第一版只支持 `mp4`
- 第一版严控文件大小和时长
- 第一版先使用本地文件系统存储
- 第一版必须有文件生命周期管理策略
- 上线前必须补一版《用户上传内容与版权说明》

## 三、什么叫“处理成功”，质量和时延底线是什么

### 要回答的问题

对用户来说，系统什么时候算“真的有用”？是转写成功就算成功，还是必须给出可信的摘要和章节？用户愿意等待多久？什么质量问题是第一版可以接受的，什么不可以？

### 当前 PRD 的问题

PRD 写了完整处理链路：

- 音频提取
- ASR 转写
- AI 内容分析
- 生成摘要
- 章节划分
- 笔记关联

但没有定义：

- 哪个结果是第一优先级
- 哪些结果失败时可以降级
- 处理成功率和处理时长的最低标准
- 怎样评估摘要和章节质量是否达标

如果不先定义，开发会很容易陷入“技术完成了，但用户体验仍然不成立”的状态。

### 推荐答案

推荐把第一版“处理成功”的定义收敛为：

**用户在上传学习类视频后，系统能在可接受时间内输出可读摘要和可点击章节，并且章节跳转大体可用。**

推荐第一版质量目标：

- 转写文本允许有少量错字
- 摘要必须能覆盖视频主要主题和关键结论
- 章节划分允许不完美，但不能完全失去结构
- 章节时间戳允许有小幅误差，但必须具备可导航价值

推荐第一版时延目标：

- 10 分钟以内视频：尽量在 `3 分钟` 内完成
- 30 分钟以内视频：尽量在 `10 分钟` 内完成
- 2 小时以内视频：允许更久，但必须让用户看到明确状态和阶段进度

### 推荐的降级策略

第一版不要把“所有步骤都成功”作为唯一成功标准，而要允许分级成功：

- A 级成功：摘要 + 章节 都成功
- B 级成功：摘要成功，章节质量一般，但可展示
- C 级成功：转写成功，但摘要失败，此时允许提示稍后重试，不要直接伪装成成功
- 失败：转写失败，或结果完全不可读

### 推荐的产品判断标准

第一版不是追求“学术级准确率”，而是追求“用户愿不愿意继续用”。

所以更重要的验证指标是：

- 用户是否真的打开摘要页
- 用户是否点击章节跳转
- 用户是否基于结果创建笔记
- 用户是否愿意再次上传第二个视频

### 建议直接定下来的结论

- 第一版结果优先级：`章节摘要 > 章节导航 > 笔记`
- 第一版成功定义：必须至少给出可读摘要或可用章节，不接受空结果成功
- 第一版必须支持失败重试和错误提示
- 第一版先用“用户行为验证价值”，而不是过度追求模型指标

## 推荐的 MVP 范围

如果以上三题采用本文推荐答案，那么第一版建议范围如下：

- 用户注册/登录
- 本地视频上传
- 视频基础信息存储
- 音频提取
- Whisper 转写
- AI 生成摘要
- AI 生成章节与时间戳
- 结果页展示摘要和章节导航
- 用户创建基础笔记
- Dashboard 展示最近处理记录

明确不进入第一版的内容：

- URL 导入
- 多平台内容抓取
- 多人协作
- 社区分享
- 复杂知识库能力
- AI 测试题
- 学习计划

## 实现前必须拍板的决策项

正式开发前，建议你把下面这些问题逐项明确，并形成最终版本：

| 决策项 | 推荐答案 |
|------|------|
| 第一版服务谁 | 在线学习者 |
| 第一版场景 | 看教程/课程后快速理解与定位重点 |
| 第一版最小价值 | 摘要 + 章节导航 |
| 视频来源 | 仅本地上传 |
| URL 导入 | 暂不支持 |
| 支持格式 | 先只支持 `mp4` |
| 文件大小限制 | `1GB` |
| 视频时长限制 | `2 小时` |
| 原视频保留时间 | `7 天` |
| 音频保留时间 | `24 小时` |
| 文本和摘要保留 | 长期保留 |
| 成功定义 | 至少输出可读摘要或可用章节 |
| 核心指标 | 摘要页打开率、章节点击率、笔记创建率、二次上传率 |

---

## 一句话版本

如果要把这个项目做成，第一版最该先回答的不是“还能加什么功能”，而是：

**到底服务谁、边界在哪、以及什么结果才算真的对用户有价值。**

这三件事先定下来，后面的技术实现、数据库设计、任务队列、模型选择、页面结构都会顺很多。
