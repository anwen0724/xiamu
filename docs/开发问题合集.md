# 开发问题合集

## 1. 文档目标

本文档用于沉淀项目开发过程中遇到的通用环境问题、工具链问题与排查结论，避免同类问题重复定位。  
本文件主要记录“问题现象、原因分析、修复方案、影响范围与操作步骤”，便于后续快速复用。

## 2. 使用说明

- 优先记录会影响本地开发、调试、构建或文档阅读的问题
- 结论尽量写清楚“为什么发生”与“怎么修复”
- 若问题只影响某一模块的业务实现，优先记入对应模块文档
- 若问题属于开发环境、终端、编码、依赖安装等通用问题，可记录在本文档

### 3.1 PowerShell 读取 UTF-8 中文文档出现乱码

#### 问题现象

在仓库中使用 PowerShell 读取 `docs/` 下的中文 Markdown 文档时，文件在编辑器中显示正常，但在终端或 CLI 输出中出现类似以下乱码：

```text
瑙嗛
鏂囨。
寮€鍙?
```

表现为：

- 文档文件本身内容正常
- 本地编辑器或 IDE 中显示正常
- 终端读取、命令输出或工具抓取输出时出现乱码

#### 原因分析

该问题通常不是文档文件损坏，而是“文件编码”和“终端输出编码”不一致导致的。

在本项目场景中，文档文件本身大概率为 `UTF-8`，但 Windows 下 PowerShell、控制台代码页或外部工具输出链路可能仍按 `GBK / CP936` 解释文本，常见触发方式如下：

- PowerShell 当前控制台代码页不是 `UTF-8`
- `[Console]::OutputEncoding` 未设置为 `UTF-8`
- `$OutputEncoding` 仍使用系统默认编码
- 读取文件时未显式指定 `-Encoding UTF8`
- 工具抓取终端输出时按另一套编码解码

典型乱码“`瑙嗛`”通常表示：`UTF-8` 文本被当作 `GBK` 进行了解码。

#### 修复目标

修复的核心目标不是修改文档内容，而是统一以下几层的编码行为：

- PowerShell 控制台输入输出编码
- 管道输出编码
- 读取文件时的显式编码
- 项目文本文件的保存编码

#### 临时修复方案

在当前 PowerShell 会话中执行以下命令，可临时将终端切换为 `UTF-8`：

```powershell
chcp 65001
[Console]::InputEncoding = [System.Text.Encoding]::UTF8
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8
```

读取文件时建议显式指定编码：

```powershell
Get-Content docs/02-MVP开发说明.md -Encoding UTF8
```

如果希望在读取前先确保当前控制台输出也是 `UTF-8`，可写为：

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
Get-Content docs/02-MVP开发说明.md -Encoding UTF8
```

#### 长期修复方案

建议在 PowerShell 的 profile 中加入默认 `UTF-8` 配置，使后续交互式会话自动使用 `UTF-8`。

推荐配置如下：

```powershell
# Default to UTF-8 for interactive PowerShell sessions
try {
    chcp 65001 > $null
} catch {
}

$Utf8NoBom = New-Object System.Text.UTF8Encoding($false)
[Console]::InputEncoding = $Utf8NoBom
[Console]::OutputEncoding = $Utf8NoBom
$OutputEncoding = $Utf8NoBom

function Use-Utf8 {
    chcp 65001 > $null
    $utf8 = New-Object System.Text.UTF8Encoding($false)
    [Console]::InputEncoding = $utf8
    [Console]::OutputEncoding = $utf8
    $OutputEncoding = $utf8
    Write-Host "Switched to UTF-8"
}

function Use-Gbk {
    chcp 936 > $null
    $gbk = [System.Text.Encoding]::GetEncoding(936)
    [Console]::InputEncoding = $gbk
    [Console]::OutputEncoding = $gbk
    $OutputEncoding = $gbk
    Write-Host "Switched to GBK (CP936)"
}

function Show-Encoding {
    Write-Host ("CodePage: " + (chcp))
    Write-Host ("InputEncoding: " + [Console]::InputEncoding.WebName)
    Write-Host ("OutputEncoding: " + [Console]::OutputEncoding.WebName)
    Write-Host ("PipeEncoding: " + $OutputEncoding.WebName)
}
```

#### PowerShell profile 修改步骤

1. 查看 profile 文件路径

```powershell
$PROFILE
```

2. 若文件不存在，则创建

```powershell
New-Item -ItemType File -Path $PROFILE -Force
```

3. 打开 profile 文件

```powershell
notepad $PROFILE
```

4. 粘贴 UTF-8 配置并保存

5. 重新打开 PowerShell，或执行以下命令重新加载

```powershell
. $PROFILE
```

6. 使用以下命令验证

```powershell
Show-Encoding
```

#### 执行策略问题

若保存 profile 后 PowerShell 启动时报错：

```text
无法加载文件 ... Microsoft.PowerShell_profile.ps1，因为在此系统上禁止运行脚本
```

通常是 PowerShell 执行策略阻止了 profile 执行。  
对本地开发机，较常见且相对稳妥的修复方式是为当前用户设置：

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

说明：

- `CurrentUser`：只影响当前 Windows 用户
- `RemoteSigned`：本地脚本可以执行，来自互联网的脚本需要签名或解除阻止
- 相比 `Unrestricted` 风险更低，更适合作为开发机默认策略

如需查看当前策略，可执行：

```powershell
Get-ExecutionPolicy -List
```

#### 修改默认 UTF-8 后的影响

将 PowerShell 默认编码切换为 `UTF-8` 后，通常对现代开发工具链是正收益，但需要注意兼容性边界。

正面影响：

- 中文文档、日志、命令输出乱码会明显减少
- 与 Git、IDE、Java、Node、Python 等现代开发工具更一致
- 读写 `UTF-8` 文本文件更稳定

可能影响：

- 某些老旧 Windows 工具仍使用 `GBK / CP936`
- 某些旧批处理脚本依赖系统默认本地编码
- 个别老程序在 PowerShell 中输出时可能再次出现乱码

因此更推荐的做法是：

- 默认将 PowerShell 设为 `UTF-8`
- 对确实依赖老编码的工具，按需临时切回 `GBK`

切回 `GBK`：

```powershell
Use-Gbk
```

切回 `UTF-8`：

```powershell
Use-Utf8
```

#### `.editorconfig` / `.gitattributes` 的作用边界

本次讨论中还确认了一个边界问题：  
即使为仓库新增 `.editorconfig` 或 `.gitattributes`，也不能直接决定 PowerShell 每次读取文件时的默认编码。

它们的作用分别是：

- `.editorconfig`：约束编辑器保存文件时的编码、缩进、换行等规则
- `.gitattributes`：约束 Git 对文本文件与换行符的处理方式

它们的主要价值在于：

- 保证项目文件尽量统一以 `UTF-8` 保存
- 减少不同编辑器或不同开发者导致的编码漂移

但它们不能替代：

- `chcp`
- `[Console]::OutputEncoding`
- `$OutputEncoding`
- `Get-Content -Encoding UTF8`

也就是说：

- `.editorconfig` / `.gitattributes` 用于约束“文件怎么保存”
- PowerShell 配置用于控制“终端怎么读取和输出”

#### 推荐结论

针对本项目本地开发环境，推荐采用以下组合方案：

1. 项目文本文件统一使用 `UTF-8`
2. PowerShell profile 默认切换到 `UTF-8`
3. 读取关键中文文件时显式指定 `-Encoding UTF8`
4. 遇到老工具兼容问题时，临时使用 `Use-Gbk`

该方案兼顾了：

- 中文文档阅读体验
- 现代开发工具链兼容性
- 老 Windows 工具的回退能力

#### 当前结论

本次乱码问题的根因不在于仓库文档损坏，而在于 Windows PowerShell 会话的编码链路未统一为 `UTF-8`。  
已通过修改 PowerShell profile 与执行策略完成本地修复，后续在当前开发机上应优先沿用 `UTF-8` 方案。

### 3.2 Maven 本地验证使用了错误的 JDK 版本

#### 问题现象

在本地执行编译命令时，Maven 报错：

```text
Fatal error compiling: 无效的标记: --release
```

进一步检查发现：

- `java -version` 输出为 `1.8.0_421`
- `mvn -version` 也绑定到了 JDK 8
- 项目 `pom.xml` 明确要求 `java.version=21`

#### 原因分析

该问题不是 Maven 编译插件本身异常，而是当前终端环境中的 `JAVA_HOME` 和 `Path` 优先指向了 JDK 8，导致 Maven 使用 JDK 8 编译 Java 21 项目。

在 JDK 8 下，编译器不支持现代 Maven 编译参数中的 `--release`，因此会直接报错。

#### 修复方案

在当前 PowerShell 会话中临时切换到 JDK 21 后再执行 Maven：

```powershell
$env:JAVA_HOME='C:\all\environments\Java\jdk21'
$env:Path='C:\all\environments\Java\jdk21\bin;' + $env:Path
mvn.cmd -q -DskipTests compile
```

执行测试时同样使用 JDK 21：

```powershell
$env:JAVA_HOME='C:\all\environments\Java\jdk21'
$env:Path='C:\all\environments\Java\jdk21\bin;' + $env:Path
mvn.cmd -q test
```

#### 补充说明

本机环境中已存在多个 JDK 版本，包括：

- `C:\all\environments\Java\jdk-1.8`
- `C:\all\environments\Java\jdk11`
- `C:\all\environments\Java\jdk17`
- `C:\all\environments\Java\jdk21`

因此问题并非“缺少 JDK 21”，而是“终端默认绑定了 JDK 8”。

#### 当前结论

本项目后续本地构建与测试应统一使用 `JDK 21`。  
若继续沿用当前默认的 JDK 8 环境，编译和测试命令都不具备稳定可重复性。

### 3.3 当前 PowerShell 下 `mvnw.cmd` 无法正常启动

#### 问题现象

直接执行项目提供的 `mvnw.cmd` 时，输出如下错误：

```text
Cannot start maven from wrapper
```

伴随 PowerShell 报错：

```text
icm : Cannot index into a null array.
```

#### 原因分析

当前本地 PowerShell 环境下，`mvnw.cmd` 所依赖的 wrapper 启动逻辑未能正常解析脚本自身内容，导致 wrapper 无法启动 Maven。

该问题发生在 Maven Wrapper 的 PowerShell 启动链路，而不是项目代码本身。

#### 当前处理方式

本次开发验证未继续依赖 `mvnw.cmd`，而是直接使用本机已安装的 Maven，并显式切换到 JDK 21：

```powershell
$env:JAVA_HOME='C:\all\environments\Java\jdk21'
$env:Path='C:\all\environments\Java\jdk21\bin;' + $env:Path
mvn.cmd -q test
```

#### 当前结论

在当前开发机环境下，`mvnw.cmd` 暂不作为稳定验证入口。  
后续本地验证默认使用 `mvn.cmd + JDK 21`，如需恢复 Wrapper，可再单独排查其 PowerShell 启动兼容性。

### 3.4 前端视觉改版多次偏离参考图与已确认约束

#### 问题现象

在首页与详情页多轮视觉收口过程中，虽然每轮都在参考目标站点或参考截图，但页面仍多次出现以下偏差：

- 自行补入用户明确不要的局部背景染色
- 将页面做成双栏或卡片页，而不是用户要求的单列首屏或工作台布局
- 导航栏宽度、居中关系、页面留白与参考目标不一致
- 用户已经明确否定的设计点在后续轮次又被加回

#### 原因分析

根因不是单次 CSS 调整失误，而是改版流程本身没有先固定“硬约束清单”。

具体表现为：

- 先开始做视觉发挥，再回头对照参考图
- 没有把用户明确说过的“必须 / 禁止”项沉淀成可执行检查项
- 每一轮修改后没有逐条回查约束，只做了主观判断

#### 修复方案

后续涉及参考图、参考站或设计复刻的页面改版时，统一按以下顺序执行：

1. 先抽取硬约束清单  
   例如：是否全宽、是否单列、是否允许局部背景色、是否保留大标题、文案密度要求等。
2. 再输出本轮实现方案  
   明确目标、改动范围、涉及文件、完成标准。
3. 改动完成后逐条回查  
   不再只凭“感觉更好看了”判断，而是逐项确认是否满足已确认约束。

#### 当前结论

当前前端视觉改版必须遵循“先约束、再实现、后验收”的方式。  
对用户已经明确否定的设计点，后续轮次不能擅自加回。

### 3.5 Dashboard 状态筛选切换时页面抖动

#### 问题现象

在 Dashboard 中切换 `全部 / 处理中 / 等待中 / 已完成 / 失败` 等筛选时，页面出现明显抖动，主要表现为：

- 切换时列表区域高度先塌陷再恢复
- 某些状态切换时页面会出现左右轻微跳动

#### 原因分析

该问题由两个原因叠加导致：

1. 切换筛选后，列表查询先进入 loading，结果区高度瞬间变化
2. 当列表内容减少时，浏览器右侧滚动条消失，视口宽度改变，导致页面左右抖动

#### 修复方案

- 在 Dashboard 查询中保留上一次结果，避免筛选切换时列表先被 loading 文案替换
- 给列表结果区增加更稳定的最小高度，减少内容高度骤变
- 在全局样式中固定纵向滚动条，避免滚动条显隐引起的横向跳动

#### 当前结论

前端列表页的“页面抖动”要同时检查：

- 查询切换时的内容高度变化
- 浏览器滚动条显隐导致的视口宽度变化

只处理其中一个因素，通常不能彻底解决问题。

### 3.6 浏览器缩放比例影响页面视觉判断

#### 问题现象

在首页视觉评审过程中，一度出现“页面整体缩小 / 文字偏大 / 布局位置不对”的判断偏差，后续确认是浏览器缩放比例不是 `100%` 导致的。

#### 原因分析

页面视觉评审默认假设浏览器处于正常缩放比例。  
当缩放比例被修改后，以下判断都会失真：

- 页面留白是否过大
- 标题和卡片是否偏大
- 首屏内容是否偏上或偏下

#### 修复方案

- 在视觉评审前先确认浏览器缩放比例是否为 `100%`
- 若发现是缩放比例问题，先恢复正常缩放，再决定是否真的需要改布局
- 设计微调时优先基于“正常缩放”结果判断，不直接根据异常缩放场景改代码

#### 当前结论

后续所有页面视觉评审前，默认先确认浏览器缩放比例。  
避免把本地浏览器设置问题误判为页面布局问题。

### 3.7 小改动频繁写入模块文档导致记录冗余

#### 问题现象

在前端页面连续微调过程中，模块文档几乎每一轮小改都追加一条记录，导致：

- 文档冗长
- 同类信息重复
- 真正有价值的阶段性变化被淹没

#### 原因分析

问题不在于文档需要维护，而在于文档更新粒度过细。  
将“一个独立可说明功能”和“一个很小的样式微调”混用同一套记录方式，会导致文档快速失真。

#### 修复方案

- 模块文档只记录可独立说明的阶段性结果
- 连续小样式调整不逐轮记文档
- 需要补记录时，优先合并成一次阶段总结，而不是流水账

#### 当前结论

后续前端页面微调默认不逐轮更新模块文档。  
只有完成一段可独立说明的页面重构或阶段性收口后，再补一次总结性记录。
